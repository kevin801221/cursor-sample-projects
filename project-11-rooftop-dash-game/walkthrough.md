# Walkthrough：在 Cursor 上把 Rooftop Dash 一步一步做出來

> 這份文件帶你從零做出 **Rooftop Dash**——一個有敵人、金幣、多關卡的平台跳躍遊戲，並親手證明一件事：**邊寫邊玩、邊玩邊改的疊代開發，比一口氣寫完然後測試更少踩坑。**
> 你會學到三件事：怎麼用一頁 GDD 鎖定功能範圍、怎麼用八欄位 prompt 模板給 AI 清晰指令、為什麼沉默故障（程式跑得好但邏輯錯）必須靠實際遊玩才能發現。
>
> 文中有四種標記，幫你少走彎路：
> - 🔍 **名詞卡**：專有名詞的白話解釋 + 生活比喻
> - ❓ **想一想**：先自己想，再往下看答案
> - ✅ **預期看到**：每個指令跑完的正常畫面長什麼樣
> - 🧯 **卡住的話**：常見翻車點與救援方式

## 🚦 開始前檢查清單（先做這五件事，做的當天才不會卡）

1. **裝好 Node.js 18+ 與 npm、跑一次 `npm run dev`**——第一次冷啟可能要 1–2 分鐘裝套件。先在家或現在這一刻測過，啟動只要十來秒，真正開始時會更順。
2. **用 Ask Mode 把 GDD 產出一遍、親自玩一遍遊戲**——最重要。不跑過一次遊戲，你沒有「手感」，讀到 `setMaxVelocity()` 那段就會問「為什麼這麼關鍵？」，往下讀就懂了。
3. **試著改一個手感參數（例如跳躍力）、看著遊戲即時改變**——這就是「常數置頂」的威力。改 constants.js 然後看遊戲馬上反應，比只讀文字印象深刻十倍。
4. 每跑完一個指令就對照文中的「✅ 預期看到」——判斷得出「這是正常的」還是「翻車了」，除錯速度差十倍。
5. 如果網路卡或電腦卡住：第 4 節「高速移動時碰撞失效」的修復過程已經詳細寫下來了，對著步驟走就行，不用靠現場除錯。

## 🎬 開場故事：樂高城堡的三層架構

想像一下，今天不是寫遊戲，是在用樂高蓋一座城堡。有些人拿到一大盒積木，就直接開始疊——疊著疊著發現城門太小、樓梯接不上、屋頂會塌。有些人呢，先拿出一張紙，畫一頁設計圖，定出城堡要多寬、城門高度多少、最後幾層只蓋觀景台——這就是 GDD。

更聰明的做法是：不是從塑膠粒開始自己做積木，而是用一大盒「樂高特殊積木」——裡面已經有「重力」、「碰撞」、「動畫」這樣的現成積木。這就是遊戲引擎 Phaser——你不用自己寫物理公式，直接疊積木。

最後，把城堡蓋起來不是一次到位。先蓋地基——檢查積木有沒有卡——再蓋一層牆、檢查有沒有歪、再加屋頂。每一步完成後，手拿著城堡轉一圈「這層是不是做對了」。這就是疊代開發，邊蓋邊玩、邊玩邊改。

一秒鐘在現實裡翻 60 頁手翻書，翻得越快城堡越平滑；翻得太慢（幀率太低）你看不清楚；有人跑得很快、一幀移動超過積木寬度，手翻書會「跳過」他，他就穿過城門了——這是高速穿過平台。所以遊戲開發，速度、幀率、碰撞偵測是一個算術題，不是魔法。

這個比喻會貫穿全文，記住這三層：

| 樂高類比 | 遊戲開發 | 技術 |
|---|---|---|
| 一頁紙的設計圖 | GDD（遊戲設計文件） | 明確定出這版本做什麼、不做什麼 |
| 現成的特殊積木（重力、碰撞已內建） | 遊戲引擎 Phaser 3 | 不用自己寫物理，套用現成函式 |
| 一秒翻 60 頁手翻書的視覺幻覺 | 遊戲迴圈（每秒 60 幀） | 每幀 16.7ms 內要算完所有位置、碰撞 |
| 翻太快穿過人偶 | 高速穿過平台（沉默故障） | 單幀位移超過物體寬度 → 物理引擎跳過碰撞檢測 |

## 1. 先懂概念：GDD、疊代開發、四大坑

### 1.1 GDD（Game Design Document）是什麼

在寫任何一行遊戲程式前，先問自己三個問題：這個遊戲玩什麼？怎麼贏？有什麼敵人或物件？最重要的是第四個問題：**這版本不做什麼**。沒有答案，就開始亂改，改著改著會發現需求無限，永遠做不完。

GDD 不是程式碼，是一份**一頁紙的遊戲設計清單**——用白話定義這個遊戲玩什麼、怎麼贏、有哪些敵人或物件。最重要的是**明確列出 Scope Cut**：這版本不做什麼。

沒有 GDD 時：
- 對 Agent 說「加個遊戲」，它會幫你加背景、加配樂、加血條、加數值平衡……回過神來就花了 20 小時
- 新對話 Agent 忘記你上一版調過的手感參數

有 GDD 時：
- 每個功能指令都對應 GDD 裡的一個需求，超出需求的需求直接擋掉
- 把關鍵數值寫在 GDD 裡，新對話一樣找得著

**最小 GDD 範本**（直接抄到 `GDD.md`）：

```markdown
# Rooftop Dash — Game Design Document

## 核心玩法
- 角色跳過屋頂平台躲敵人、收金幣
- 目標：收集當前關卡所有金幣 → 打開出口門 → 進下一關

## 操作
- ← → 移動
- SPACE 跳躍
- P 暫停 / R 重來
- M 返回菜單

## 敵人與碰撞
- 敵人在平台上來回巡邏
- 碰到敵人扣一命（三條命遊戲結束）
- 踩敵人頭會消滅敵人、得分

## 物件
- 平台：靜態碰撞，玩家在上面跳躍
- 敵人：移動碰撞，傷害玩家
- 金幣：收集物，吃完才開門
- 出口門：只有收完金幣才可通行

## 關卡
- 至少 2 關（Scope Cut：不做動態生成、不做無限模式）

## Scope Cut（本版本不做）
- ✗ 攻擊系統（踩敵人頭除外）
- ✗ Boss 戰
- ✗ 武器或道具
- ✗ 多人模式
- ✗ 動態地圖生成
- ✗ 成就、排行榜
```

> 🔍 **名詞卡：Scope Cut（範圍切割）**
> 白話：「這版本不做什麼」的清單。像餐廳菜單印出來前，老闆會決定「這版本只做 10 道菜，不做 15 道」，這樣廚房才不會每天都在嘆「為什麼永遠做不完」。

### 1.2 疊代開發 — 一次改一個功能

不是一口氣做完整個遊戲，而是一個一個功能疊上去。好處是：每次只改一個東西，壞掉也知道是這個環節的問題；每次完成後玩一遍，確認新功能沒有破壞舊功能。

步驟如下：

1. **第 0 版本**：空場景 + 玩家會動（驗證 Phaser 能跑）
2. **第 1 版**：加平台、加跳躍、加重力（驗證物理引擎）
3. **第 2 版**：加敵人、敵人會巡邏、碰撞扣命（驗證碰撞判定）
4. **第 3 版**：加金幣、加出口門、出口門判邏輯（驗證狀態機制）
5. **第 4 版**：加音效、加暫停 UI（驗證整體體驗）

每版完成後玩一次，確認沒沉默故障。如果某版改壞了，能快速定位是哪個迭代。

> 🔍 **名詞卡：遊戲迴圈（game loop）**
> 白話：遊戲的心臟。每秒跳 60 次，每跳一次就：讀一下玩家按了什麼鍵 → 算一下新的位置 → 檢查有沒有碰撞 → 畫在螢幕上 → 重複。像你的心臟每秒跳 80 下，每跳都在抽血、抽出去、循環。

### 1.3 vibe coding 四大坑

讓 AI 寫遊戲的四個陷阱。前三個 AI 不用負責，你自己要設防；第四個要在 GDD 裡明確寫出 Scope Cut，不然 AI 會順著需求越做越多。

**坑 1：70% 問題**
- AI 快速產出七成，剩下三成邊界情況要人工檢查
- 例：「敵人會巡邏」✓ 敵人「碰到牆轉身」✗ 敵人「掉下平台消失」✗
- 對策：每個迭代完親自玩，盡量觸發邊界情況（快速移動、連續碰撞、卡角落）

**坑 2：沉默故障**
- 程式碼能跑、沒報錯，但邏輯錯
- 例：分數算了但沒存進 registry、敵人接觸檢測用錯方法、暫停時物理沒停
- 對策：有懷疑時插 `console.log` 驗證流程，尤其是「狀態應該改但沒改」的情況

> 🔍 **名詞卡：沉默故障（silent failure）**
> 白話：程式**不會尖叫**（沒報錯），但**暗中壞掉**。像車子引擎能轉、轉盤轉得很快，但齒輪其實沒咬合——你開著就很順，但實際沒在走。最可怕的錯誤，因為你一開始看不出來。

**坑 3：記憶失效**
- 長對話被壓縮、新對話 Agent 忘記你調的手感參數
- 例：「跳躍力改成 800 了」下一個對話 Agent 又用預設 600
- 對策：所有可調數值都寫進 `constants.js`，在 GDD 或註解裡也標註一遍

**坑 4：範圍蔓延**
- 「加個暫停功能」變成「加暫停、加 UI、加半透明遮罩、加提示文字、加暫停時進度條」
- 對策：八欄位模板的 Do NOT 欄位一定要填，告訴 Agent「本版本不要做什麼」

### 1.4 物理引擎常見錯誤

前面 RLS 課程說「`USING (true) = 沒開`」。遊戲開發的等效錯誤是：速度沒限制。結果一樣：看起來有防線，其實全通。

| 問題 | 後果 | 為什麼會壞 |
|---|---|---|
| `setMaxVelocity()` 沒呼叫 | 高速跳躍穿過平台（沉默故障） | 物理引擎跳過碰撞檢測 |
| 敵人碰撞用 overlap 沒加 check | 角色卡在敵人裡面 | 一直在碰撞，沒有推開邏輯 |
| 狀態存在 Scene 實例而不是 registry | 重開關卡狀態歸零或殘留 | Scene.switch 丟掉所有 this 變數 |
| refreshBody 沒呼叫 | 改了碰撞體尺寸後新碰撞沒生效 | 物理引擎用的是舊的邊界 |

這些都是**程式碼能跑、沒報錯、但破壞遊戲體驗**的錯。必須自己玩測才發現。

> 🔍 **名詞卡：hitbox（碰撞箱）**

```markdown

alwaysApply: true

# Rooftop Dash 架構規則

## 一檔一職責

- `input.js` 只管鍵盤輸入，禁止包含邏輯
- `constants.js` 只放可調數值（速度、重力、敵人 HP、金幣得分等）
- 每個場景各自一檔 (`scenes/XXXScene.js`)，不要把多個場景混在一起
- `prefabs/` 資料夾裡的類只放初始化和方法，不要依賴外部場景狀態

## 常數置頂

- 速度、重力、跳躍力、敵人 HP、碰撞體尺寸一律寫進 `constants.js`
- 禁止在場景檔寫死數值（例：禁止寫 `setVelocityY(-400)`，改用 `setVelocityY(-CONSTANTS.JUMP_FORCE)`)
- 調手感時只改 `constants.js`，不用翻場景檔

## 禁止規則

- 禁止建立第二個 Phaser Game 實例。全專案只有 main.js 裡那一個
- 禁止在 Scene 實例上直接存分數、命數、收集計數。一律改用 `registry.set('key', value)` 與 `registry.get('key')`，這樣切換場景不會遺失

## 一定要做

- 改完碰撞體尺寸一定呼叫 `physics.body.refreshBody()`
- 敵人、玩家速度一定要設 `setMaxVelocity()`，防止高速穿過平台
- 每個迭代完親自玩一遍，尤其是快速移動、連續碰撞、邊界情況
```

**`.cursor/rules/phaser.mdc`**（按需載入）：

```markdown
---
description: Phaser 3 開發慣例
globs: ["src/scenes/**/*.js", "src/prefabs/**/*.js"]
---

- 碰撞檢測用 physics.overlap 判傷害，用 physics.collider 判支撐（互相推動）
- 敵人位置改動後一定呼叫 refreshBody，不然碰撞體還在舊位置
- 移動速度大於平台厚度要設 setMaxVelocity，否則高速穿過
- 狀態（分數、命數、金幣計數）存 registry，不存 this，這樣 scene.switch 不會遺失
```

✅ **預期看到**：重啟 Cursor，對 Agent 說「把 setVelocityY(500) 改成用常數」，Agent 應該拒絕並說這違反規則「禁止寫死數值」。

## ⭐ 7. 情境演練：修高速移動時碰撞失效（一定要親自試的一幕）

現在進入本文檔的精髓。我們要故意做一個會壞掉的遊戲、讓它壞、然後修好。這樣你才會深刻理解「為什麼 `setMaxVelocity()` 這麼重要」。

### 症狀

玩家快速下墜時偶爾直接穿過平台，畫面沒有任何錯誤訊息。

### 怎麼診斷

**Step 1：切到 Debug Mode，插入 log**

對 Cursor Agent 說：

> 在 PlayScene.js 的 update 迴圈加上 console.log 印出玩家的速度與位置，特別是下墜速度。測試快速跳躍後下墜，觀察 log。

預期看到：玩家下墜速度越來越大（受重力加速），最後一幀位移可能超過 30px。

✅ **預期看到**：console 裡有 `Player Y velocity: 456, position Y: 320` 這樣的 log，數字越來越大。

**Step 2：發現根本原因**

現在發現一個數學問題：Phaser 預設 60fps，每幀 16.67ms。平台厚度假設 12px。如果一幀位移超過 12px——比如玩家下墜速度是 500px/s，一幀就移動 8.3px 還好，但快速跳躍加速後可能 30px——物理引擎會怎樣？

跑太快穿過平台是幀率與碰撞體厚度的算術題：
- Phaser 預設 60fps（每幀 16.67ms）
- 平台厚度假設 12px
- 一幀位移超過 12px 時，物理引擎的連續碰撞檢測會失效——這幀的起點在平台上、終點在下方，引擎判定「沒碰」

> 🔍 **名詞卡：碰撞偵測（collision detection）**
> 白話：每幀檢查「兩個 hitbox 有沒有重疊」。如果位移太大，引擎會「跳過」中間的檢查——像手翻書翻太快，某一頁就沒看到。

**Step 3：套用 setMaxVelocity**

對 Cursor Agent 說：

> 在 PlayScene.js 初始化玩家時，加上 `player.body.setMaxVelocity(200, 400)`。第一個數字限制左右速度，第二個限制上下速度。測試：重新快速下墜，檢查玩家不再穿過平台。

預期結果：即使連續跳躍，玩家下墜速度也不會超過 400px/s，相當於 6.7px/frame（60fps 時），小於平台厚度，不穿過。

✅ **預期看到**：console.log 顯示每幀位移都小於平台厚度（12px），快速跳躍後下墜不穿過平台。

🧯 **卡住的話**：如果修完還穿過，代表平台厚度設得太小。問 Agent：「看起來還是穿過，平台是不是太薄？試試改 constants.js 的 PLATFORM_HEIGHT 從 20 改成 30。」讓 Agent 改完再測。

注意到沒有？這個 bug 不會報錯。程式碼完全正常運行，沒有任何警告。但遊戲就是壞了。這叫沉默故障。唯一的發現方式是：玩。親自拿著遊戲玩、快速移動、試著觸發邊界情況。這就是為什麼要一直說「每個迭代完都要親自玩一遍」。

## 9. 常見坑排錯速查

多數遊戲 bug 都能從這張對照表快速定位（學生課後卡關，九成在這張表裡）：

| 問題 | 常見原因 | 解法 |
|---|---|---|
| 角色卡在平台裡 | `refreshBody()` 沒呼叫 | 改尺寸後務必呼叫 `physics.body.refreshBody()` |
| 分數沒儲存 | 分數存在 Scene 實例上 | 改用 `registry.set('score', value)` |
| 高速穿過平台 | 單幀位移超過平台厚度 | 用 `setMaxVelocity()` 限制速度 |
| 部署後資源 404 | base 路徑與 repo 路徑不符 | 確認 `vite.config.js` 的 `base` 設定 |
| 敵人卡玩家 | 碰撞用 collider 而不是 overlap | 敵人傷害用 overlap；支撐用 collider + `immovable` |
| 命數改不了 | 狀態存在 this 而非 registry | 改用 `registry.set/get` 保存 |
| 暫停時物理沒停 | 只暫停了場景update 沒暫停physics | 用 `scene.physics.pause()` 同時停物理 |
| 暫停遮罩疊層 | 沒檢查暫停狀態就疊遮罩 | 判斷 `scene.isPaused()` 再決定動作 |
| 金幣卡在牆裡 | 金幣初始位置沒檢查碰撞 | 保證金幣初始座標不在碰撞體內 |
| 新對話 Agent 忘記手感參數 | 參數只留在對話，沒寫進 constants | 所有可調數值都寫進 constants.js，下次對話才找得著 |

## 課後思考題

### 問題 1：「為什麼一定要寫 GDD？」

❓ **想一想**：假設現在對 AI 說「幫我做一個遊戲」，AI 可能會做什麼？

**答案**：加背景、加配樂、加血條、加敵人 AI、加關卡編輯器……最後會說「停停停，我只要基本玩法」，但時間都花了，改動也多，容易引入新 bug。

### 問題 2：「為什麼 `setMaxVelocity()` 不是可選的？」

❓ **想一想**：看到玩家快速下墜時會穿過平台。假設不修這個，玩家遇到的狀況是什麼？

**答案**：隨機穿過平台——有時穿、有時不穿，玩家會以為是自己操作有問題，然後放棄遊戲。最糟的是，這個 bug 在測試時可能沒觸發（取決於幀率、速度、平台厚度的配合），發佈到線上才出現。

### 問題 3：「為什麼狀態要存在 registry 而不是 Scene 實例？」

❓ **想一想**：假設第一關把 `this.lives = 3` 存在 PlayScene，第一關結束時 `this.scene.switch()` 切換到第二關。第二關的 PlayScene 是一個新的 Scene 實例，它的 `this.lives` 會是多少？

**答案**：undefined（或報錯）。因為第一關的 this 已經被丟掉了。改用 registry 後，`registry.get('lives')` 在任何場景都能取到上一關的命數。

## 9. 帶走的三句話

如果整份文檔只能記住三件事，就這三句。

1. **動手寫程式前先用 Ask Mode 產出 GDD，列出 Scope Cut 清單鎖定範圍**——沒有 GDD 時範圍蔓延最快，「加個暫停」最後變成「加暫停、加菜單、加設定、加排行榜」；GDD 裡明確列出「這版本不做什麼」，對 Agent 說「超出 Scope Cut 的需求一律擋掉」。

2. **結構化 prompt 模板八欄位能大幅降低指令模糊造成的返工**——Goal 定義單一目標、Do NOT 畫出範圍邊界、Done when 給出可驗證的完成條件，Agent 才不會超出預期；最常見的返工原因就是指令模糊造成的「完成標準不一致」。

3. **沉默故障不會報錯，必須靠實際遊玩測試才能發現**——高速穿過平台、分數沒存進 registry、敵人碰撞設錯都能跑、都看不出問題，唯一的發現方式是自己玩一遍、觸發邊界情況；長對話時把關鍵手感數值寫進 Rules 而不是只留在對話裡，下次對話才找得著。
